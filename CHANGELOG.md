### Changed

- Upstream 0.8.3 (710e173: #103, #104, #105, #107) merged: upstream's Cursor CLI retries (a shared budget of 10 transport and 3 server retries across provider recoveries, tool steps and host retries; a Run cut after only text, reasoning or an unfinished tool row is retried by the host; a drop right after completed tools rebuilds from their results, here also when Cursor announced those calls, as it does for nearly every tool, which upstream counts as work the history cannot hold; read-idle at 30 s, with heartbeats keeping a Run alive) replace the fork's own retry of a stall it could not replay, and upstream's turn checkpoint replaces the fork's resume from the checkpoint a resumed Run started from. Capacity refusals keep the fork's six attempts with a longer backoff, outside that budget. Upstream's failed-shell handling (#104) replaces the fork's, now for unary results too, and upstream's early edit rows (#107) replace the fork's check for an edit whose read goes to the host
- Run messages over 1 KiB go to Cursor gzip-compressed, as Cursor CLI sends them: the Run request and the conversation blobs Cursor asks for again at the start of every new Run (3.5 MB at 700k tokens of context, about 4× smaller compressed). The first token of a new turn arrives about 1.2 s sooner at 700k tokens and 0.4 s sooner at 300k; small conversations don't change. If Cursor refuses a compressed Run (`unimplemented`, HTTP 415, or a decompression error), the Run is sent again once uncompressed, outside the retry budget, and later Runs to that host stay uncompressed until the provider restarts. The debug log now also splits each Run's time to first token between Cursor's server and the model, from Cursor's own timing message
- Run connections advertise an 8 MiB stream and 16 MiB connection receive window instead of Node's and Bun's 64 KiB. Cursor's checkpoint blobs at the end of a turn on a large conversation are often several hundred KB compressed (1.4 MB uncompressed at 570k tokens), and at 64 KiB per round trip they took about a second to arrive, delaying the turn's end in OpenCode by as much.
- A turn's end reaches OpenCode before its restart snapshot is written (gzip and file write, about 0.1 s at 700k tokens). The snapshot is still written in order with the session's other saves, and a shutdown waits for it. If OpenCode stops the stream before it has read the turn's last parts, the step is kept as stopped and saved again, as when a Stop arrived during the save before.
- A Run starts without the HTTP/2 health-check ping when its connection received data in the last 10 seconds, as Cursor CLI does, which saves a round trip to Cursor on most Runs. If that connection turns out to be dead before Cursor answers (reset, refused stream, or a GOAWAY that excludes the Run), the Run is sent once more on a new connection; once Cursor has answered it is never sent again
- Upstream #98 and #99 (fcc986a) merged: upstream's verbatim shell output replaces the fork's, and upstream's Task attachment reads replace the fork's (only reads of a listed attachment are answered, `~/` paths are expanded, an unstatable attachment reports its error). - Upstream #78 (530bd29) merged: upstream's history images per checkpoint (the same snapshot fields 16/17) and frame-arrival numbering replace the fork's copies. The fork keeps following a conversation rekey with the images its checkpoint holds and still sends a stopped turn's images again even when Cursor ends that turn on a checkpoint. ### Fixed

- Cursor's capacity refusals and model-provider errors no longer reach OpenCode as a 429, which OpenCode 2 reads as a rate limit and T3 titles "Usage limit reached". Cursor sends both with the Connect code `resource_exhausted`; its `ErrorDetails` now decide the status. High Load (`ERROR_RESOURCE_EXHAUSTED`) ends, after the provider's own attempts, with "Cursor has no capacity for <model> right now (Cursor: High Load): a limit on Cursor's side, not on your key or usage …". `ERROR_PROVIDER_ERROR` ends with "<Anthropic, OpenAI, Google, xAI or The model provider> rejected or failed the request (Cursor ERROR_PROVIDER_ERROR, provider status <its status>). This is not your key or your usage …". Both now use status 400, and OpenCode still doesn't retry them. Login and API-key errors are 401 whatever the Connect code, usage, spend and plan limits 402 (`provider.quota`), and account rate limits stay 429. An API-key rate limit or provider error that Cursor marks retryable now uses the normal retry budget instead of the capacity attempts and their "no capacity" message
- The debug log (`CURSOR_PROVIDER_DEBUG`) keeps its previous part when it reaches its size cap: the file moves to `<file>.1`, replacing an older one, and a fresh file starts with a `debug: size-cap rotate previous=<file>.1` line, where the log was truncated and everything before was lost, so under load it held only the last few minutes. `CURSOR_PROVIDER_DEBUG_MAX_BYTES` sets the cap in bytes (default 10 MiB); a value that isn't a positive whole number keeps the default
- An AskQuestion option whose label contains ", " (such as "Yes, do it (Recommended)") reaches Cursor as that selected option, not as the user's own typed answer. The answer was split at every ", ", so no piece matched the label
- An edit of an existing file outside the workspace, or of one the provider can't read, no longer shows a failed `edit` row ("Cursor did not finish this tool call.") before its read. Cursor reads the file first, and for such a file that read goes to OpenCode's permission-aware `read` and ends the step, which closed the early row opened for the edit; the edit itself came in the next step. No early row opens for such an edit now.
- Web search waits out Exa's free-tier rate limit instead of failing: a 429 from Exa's keyless MCP endpoint is retried after its `Retry-After` (capped at 5 s, plus up to 1 s of jitter so parallel subagents spread out), up to six attempts within the search's budget. Before, a burst of parallel searches failed most calls with OpenCode's bare "Unable to search the web"
- A burst of web searches from parallel subagents queues instead of failing. Exa's keyless tier takes about three requests at a time per IP and refuses the rest with 429, so a burst of dozens outlasted the retries above. Without an `EXA_API_KEY`, the process now sends at most three searches to Exa at once, shared by every provider copy in the OpenCode process, and the others wait their turn in arrival order. A search's budget is now 45 s, counting its wait in line; one still waiting after 30 s fails, saying so. The 429 retry stays for other clients on the same IP. With an `EXA_API_KEY` nothing is queued
- A web search fails at once, saying how long Exa will refuse searches, when Exa's 429 asks for a wait longer than the search's budget. Exa's keyless tier also has a daily quota per IP, and once it is used up every search gets a `Retry-After` of hours (until midnight UTC); each search used to retry it six times before failing
- With an `EXA_API_KEY`, web search still uses Exa's free keyless tier first and spends the key's credit only on what keyless refuses: a search goes out with the key when all three keyless slots are taken, instead of waiting for one, or when Exa answers the keyless request with 429, instead of retrying it. Once Exa says the keyless daily quota is used up, searches go straight to the key until the time its `Retry-After` named, for every provider copy in the process. Before, a key sent every search with the key. Without a key nothing changes. The key now goes to Exa in the `x-api-key` header instead of the URL, and the debug log records which route each request took (`web-search: keyless request` or `web-search: keyed request` with the reason), never the key. A search Exa answers with an error result fails with Exa's message, such as "Invalid API key" for a wrong key: Exa sends those with HTTP 200, so they came back as the search's text, or as no results on OpenCode 2
- On OpenCode 2, compacting a session whose history no longer fits Cursor's context window no longer fails with "Compaction summary did not match the required template". OpenCode sizes its summary request at four characters per token and sent the whole history; Cursor cut the oversized message, so the model never saw the history or the summary instructions. A compaction request over 80% of the window, sized at 1.75 characters per token, now fails as too large before it reaches Cursor, so OpenCode resends the history as a transcript with long tool outputs shortened, and drops its oldest messages only if that still doesn't fit
- On OpenCode 2, a subagent's open permission, question or form prompt, and the activity of a session's tools, now keep its parent's held Cursor Run alive even when OpenCode loads the plugin and the model as separate copies of the provider: every copy shares one record of session parents, activity, running tools and open prompts
- A restart while a Run waits on host tools keeps the host notes Cursor has not acknowledged yet: the snapshot saved for a held Run now includes them, so they still reach the next user turn
- In a client that keeps plan mode as the session's own permission rules (T3's OpenCode 2 plan mode denies edits on the session until the user leaves it), CreatePlan saves and shows the plan without asking whether to start implementing, and tells the model to end the turn: no answer there could lift the client's rule, so a "Yes" left every edit denied and the model fell back to writing files through the shell. SwitchMode out of plan mode and the plan-mode reminder point to leaving plan mode in the client the same way
- Under Bun, a Run that Cursor cancels before answering is no longer sent again on a new connection when it was the last Run on a connection being closed (after a failed health-check ping, a GOAWAY or the 15-minute rotation): only a lost connection counts as Cursor not having taken the Run
- What Claude Opus 5.5 writes right before a tool call (for example the explanation before it asks you a question) shows as text again instead of disappearing into its thinking. Opus 5.5 returns that text as a progress-update thinking block, which Cursor streams like reasoning; a thinking block that follows a finished one before any text or tool call is now emitted as text
- Tool calls the model sends in one step no longer race when one depends on another: as in Claude Code, reads, searches, subagents and read-only shell commands still run together, but an edit, write, other shell command or MCP tool waits for the calls written before it, and the calls written after it wait for it, so a commit or a post written after an edit sees the edit
- When Cursor's copy of a conversation is lost (a restart without its saved state, a held Run that expired before its tool result came back, a history rewrite), the replayed history keeps every earlier tool result and tool call input whole instead of cutting each to 2,000 characters, so the model still knows what it read. Only a replay that would pass 80% of the context window shortens its oldest results first, saying so where it does; one that cannot fit still makes OpenCode compact. Replays are now sized at 1.75 characters per token, as Cursor counts dense coding sessions, instead of four, so one that passes the check really fits
- A host note that arrives while a step's tools run (a background subagent's or shell's completion report, nested `AGENTS.md` instructions, other `<system-update>` notes) reaches the model as its own message after the step's results, as Claude Code delivers them, instead of being appended to the last result. Cursor moves a long result into an `agent-tools` file and shows the model a preview, so a report appended to a long search result was never seen
- Session titles and other tool-less requests (plugin `generate` calls) no longer advertise the session's tools, and the host's instructions open the request with its message as the input, so the title model answers in one call instead of trying tools that are then refused. Compaction still advertises the session's tools
- OpenCode 2 plugin `generate.text` calls (memory recall, summaries) complete instead of waiting forever for a tool catalog ([#40](https://github.com/oakimov/cursor-opencode-provider/pull/40) by [@nkoynov](https://github.com/nkoynov))
- OpenCode 2.0 loads the AI SDK provider at the installed plugin's version instead of the latest npm release ([#41](https://github.com/oakimov/cursor-opencode-provider/pull/41) by [@nkoynov](https://github.com/nkoynov))
- A message sent while a step's tools run no longer cancels the held Run's pending results and makes the model redo them: when the Run waits on exactly that step's results, the message is injected into that Run the way Cursor CLI steers, then the results are delivered, and a message Cursor does not take, or one a later call of the step, held back or not yet sent, would follow, is sent as a follow-up when the turn ends ([#N](https://github.com/oakimov/cursor-opencode-provider/pull/N) by [@nkoynov](https://github.com/nkoynov))
- MCP tools stay on the OpenCode 2 direct tool list after a plugin reload instead of moving into Code Mode until an MCP server reconnects, and a call to a tool the host left out of the direct list points the model at `execute` when Code Mode is available instead of telling it to give the tool up ([#55](https://github.com/oakimov/cursor-opencode-provider/pull/55) by [@nkoynov](https://github.com/nkoynov))
- An exec Cursor withdraws (`ExecServerControlMessage.abort`) no longer holds its Run while OpenCode's tool keeps running, also when Cursor withdraws an exec the provider still holds back behind earlier calls of the step
- A Run without a Cursor checkpoint (after a restart, a lost Run, a foreign-history or history-rewrite rebase) keeps the host system context, subagents and MCP instructions, and replays earlier tool calls with their results: prior turns now open the user message instead of replacing Cursor's root prompt, where they dropped the rules for the rest of the conversation and the model took its own earlier work for undone. When such a history would fill more than 80% of the model's context, the provider asks OpenCode to compact first, as a foreign-history rebase already did. A user message with no reply after it is marked "no reply" in the replayed history, so a steer the model answered early, which OpenCode records after that answer, is not answered again
- A message OpenCode queues right before or after the user's own one (a finished background shell, subagent or task, a `<system-update>`) no longer replaces it: a Run sends every user message since the model's last reply, in OpenCode's order, where it sent only the last one, so on a Run with a Cursor checkpoint the user's question or the host note was lost, and without one the question was replayed as history while the note became the request ([#N](https://github.com/oakimov/cursor-opencode-provider/pull/N) by [@nkoynov](https://github.com/nkoynov))
- On OpenCode 2.0, a Cursor background shell that finishes tells the model, as OpenCode's own background shells do: a `<shell>` note with the exit code (or that it was stopped, or that its supervisor was lost) and the output's last lines reaches it at its next step, or starts a new turn if it had ended its turn, so it no longer has to keep its turn open and poll. No note is sent when the model already read the finished terminal record
- Cursor models no longer call OpenCode tools by their own names as top-level tools, which Cursor refuses with "Tool not found" (seen with MCP tools and `execute`). The system guidance called every advertised tool a direct tool to call by name, but Cursor's top-level list has only its own tools plus GetDynamicTools / CallDynamicTool. It now lists which host tools Cursor's native tools run (`read` through Read, `edit` through StrReplace, …) and which are called through CallDynamicTool, with the namespace and tool name from Cursor's catalog
- When Cursor's safety filter quietly answers with another model (Claude Opus 4.8 instead of the Opus 5.5 you picked), the turn stops at the first step Cursor marks as switched instead of going on with that model and a notice at the end. The reply says what happened and what already ran, nothing the other model wrote is kept (the next request continues from the checkpoint before the switch, on a fresh Cursor conversation), and you rephrase the request or reply `continue with opus 4.8` to let the other model answer it once. `CURSOR_ALLOW_MODEL_FALLBACK=1` keeps the previous behaviour
- A resumed Run that fails before Cursor sends a newer checkpoint resumes again from the one it started from, as Cursor CLI does, instead of ending the turn as unsafe to retry; once the Run asks the host for anything or answers an interaction, that checkpoint is no longer reused. A Run's own checkpoint from before an interaction the provider answered (a plan file, an approval) is not resumed either, so the interaction does not repeat
- A Run Cursor refuses for capacity (`resource_exhausted`, `unavailable`, HTTP 429/503) is retried over about a minute (six attempts per turn, delays from 1–2 s doubling to 15–30 s, or Cursor's retry delay) instead of three attempts within about 1.5 s, which an Opus capacity shortage outlasted. The final error says the capacity is on Cursor's side, not a limit on the key. Network errors keep the fast retries. An explicit `retry.maxAttempts` caps capacity and other retries together across the turn, and `CURSOR_ENDLESS_RETRIES` lifts the capacity limit too
- A tool call that fails or is refused reaches the model as a failure also when the plugin has not marked the result: OpenCode sends the error as plain text holding `{"error":…,"content":[]}`, and the provider reads it, so the tool gets Cursor's own result (error, permission denied, or rejected with the user's reason) instead of a success. A refused Pi write or edit gets Cursor's rejected result
- A message Cursor never checkpointed is also sent again when it was a steer Cursor did not take (sent as a follow-up Run) or a reply to a safety-filter stop, is dropped by a Stop during OpenCode's retry wait too, and is left out of a helper Run on the same session whose prompt does not hold it
- An edit's early tool row opens as `write` for an empty existing file, which the edit stays as, and not while an earlier call of the step is still on its way, so neither case shows a failed row next to the real call

A retry after a checkpoint resumes the turn's latest checkpoint, and two resumes that save nothing end the turn ([#100](https://github.com/oakimov/cursor-opencode-provider/issues/100), reported by [@nkoynov](https://github.com/nkoynov))

- On macOS, a shell command that printed nothing before being moved to the background no longer reports `head: illegal byte count -- 0`

A `maxMode` option without a picked variant lands on the model's declared max default even when Cursor declares a Fast variant (Grok 4.7 500k High, GPT-5.2 High).
